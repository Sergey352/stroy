## Важные технические ограничения Pyrus API v4 (проверено по официальной документации)

- Нельзя программно создавать/редактировать поля, шаги, маршрутизацию формы — только вручную в UI конструктора.
- При создании/обновлении задачи значение поля можно адресовать по `id`, `name` ИЛИ `code` — в проекте используется только `code`.
- Форматы value при записи (проверено эмпирически на реальных запросах, не только по докам): `catalog` → `{"item_name": "..."}` или `{"item_id": N}`; `multiple_choice` → **только** `{"choice_ids": [N]}` (текстовые `choice_names` при записи не поддерживаются, при чтении присутствуют); `date` → `"YYYY-MM-DD"` (без времени); `table` → список `{"row_id": i, "cells": [{"id": col_id, "value": ...}]}`.
- Фильтрация реестра задач (`GET /forms/{id}/register`) по значению поля работает только через числовой `id` поля (`fld{id}`), не через `code` — поэтому в ботах реестр запрашивается без фильтра по полю, а нужные задачи ищутся на стороне скрипта перебором по `code`.
- Справочники (catalogs) полноценно создаются и редактируются через API: `PUT /catalogs` (создание), `POST /catalogs/{id}/diff` (upsert/delete по ключу), `POST /catalogs/{id}` (полная синхронизация).
- Права доступа к форме: `GET/POST /forms/{id}/permissions`, уровни `administrator | manager | restricted_manager | member | none`. Менеджеров «по условию» через API добавить нельзя.
- Справочник целиком удалить через API нельзя (нет DELETE), а первую (ключевую) колонку — переименовать нельзя (`can_not_modify_first_column`). Учитывать при проектировании схемы справочника заранее.
- `POST /catalogs/{id}/diff`: если в одном запросе `upsert` два элемента с одинаковым значением первой (ключевой) колонки — 400 `validation_error` («Duplicate keys in Upsert collection»). Для составных ключей значение первой колонки должно быть уникальным в каждой строке.
