## Важные технические ограничения Pyrus API v4 (проверено по официальной документации)

- Нельзя программно создавать/редактировать поля, шаги, маршрутизацию формы — только вручную в UI конструктора.
- При создании/обновлении задачи значение поля можно адресовать по `id`, `name` ИЛИ `code` — в проекте используется только `code`.
- Форматы value при записи (проверено эмпирически на реальных запросах, не только по докам): `catalog` → `{"item_name": "..."}` или `{"item_id": N}`; `multiple_choice` → **только** `{"choice_ids": [N]}` (текстовые `choice_names` при записи не поддерживаются, при чтении присутствуют); `date` → `"YYYY-MM-DD"` (без времени); `table` → список `{"row_id": i, "cells": [{"id": col_id, "value": ...}]}`.
- Фильтрация реестра задач (`GET /forms/{id}/register`) по значению поля работает только через числовой `id` поля (`fld{id}`), не через `code` — поэтому в ботах реестр запрашивается без фильтра по полю, а нужные задачи ищутся на стороне скрипта перебором по `code`.
- Справочники (catalogs) полноценно создаются и редактируются через API: `PUT /catalogs` (создание), `POST /catalogs/{id}/diff` (upsert/delete по ключу), `POST /catalogs/{id}` (полная синхронизация).
- Права доступа к форме: `GET/POST /forms/{id}/permissions`, уровни `administrator | manager | restricted_manager | member | none`. Менеджеров «по условию» через API добавить нельзя.
- Справочник целиком удалить через API нельзя (нет DELETE), а первую (ключевую) колонку — переименовать нельзя (`can_not_modify_first_column`). Учитывать при проектировании схемы справочника заранее.
- `POST /catalogs/{id}/diff`: если в одном запросе `upsert` два элемента с одинаковым значением первой (ключевой) колонки — 400 `validation_error` («Duplicate keys in Upsert collection»). Для составных ключей значение первой колонки должно быть уникальным в каждой строке.

### Новое ТЗ (реальные требования)

1. Несколько строительных объектов одновременно в работе; их количество со временем меняется.
2. На каждый объект — смета в Excel: несколько вкладок (по инженерным системам/разделам), суммарно тысячи позиций.
3. Смету нужно перенести в Pyrus.
4. Пользователь выбирает объект и заполняет заявку на материалы.
5. Если позиции нет в перечне — система должна предложить создать её.
6. **В реальном времени** считается разница между сметой и заявкой, при превышении — красное предупреждение.

### [КРИТИЧНО] Найденный и исправленный баг: контейнеры Docker вообще не имели сети

После установки Docker контейнеры не могли достучаться даже до собственного шлюза (`172.17.0.1`, IP моста `docker0`) — 100% потерь, при этом сам хост в интернет ходил нормально. Это НЕ проблема провайдера/файрвола/хостинга — подтверждено `tcpdump`: пакеты не покидали хост даже на уровне моста, то есть проблема была локальной, внутри ОС. Перебрано и исключено по очереди: DNS (`daemon.json` с `1.1.1.1`/`8.8.8.8` — не помогло), `iptables`/`nftables` правила (выглядели корректно, полный `nft list ruleset` проверен по всем таблицам и семействам, включая `ebtables` — пусто/accept), модуль `br_netfilter` (не был загружён, загрузили — не помогло), offload-чексуммы `virtio_net` (известный класс багов с мостами на этом драйвере — тоже не помогло), перезагрузка сервера целиком (не помогло — значит не «зависшее» состояние ядра, а конфигурация, переживающая ребут).

**Настоящая причина:** `/etc/systemd/network/10-all.network` (был в системе до нас, часть стандартного cloud-образа) содержит `[Match] Name=* Type=ether` — это matches **вообще все** ethernet-интерфейсы, включая veth-пары, которые Docker создаёт для каждого контейнера (сам мост `docker0` — тип bridge, не ether, поэтому он оставался «unmanaged», а вот его veth-порты — ether, значит подпадали). systemd-networkd брал эти veth под управление и пытался поднять на них DHCP — конфликтовал с настройкой, которую делает сам Docker, и порт моста лихорадило (в `dmesg` было видно: `entered forwarding state` → почти сразу `entered disabled state`).

**Исправление:** добавлен `/etc/systemd/network/00-docker-unmanaged.network` (сортируется раньше `10-all.network` по имени файла — systemd-networkd берёт первый подходящий файл):
```ini
[Match]
Name=veth* docker0

[Link]
Unmanaged=yes
```
Затем `systemctl restart systemd-networkd && systemctl restart docker`. После этого — 0% потерь и до шлюза, и до интернета. **Если VDS когда-нибудь пересоздадут/переустановят с нуля — этот файл нужно будет создать заново**, сам по себе он не появится.

## [ВАЖНО] Колонки «Сумма» в справочнике «Смета» — сессия 2026-08-21

Пользователь заметил: в справочнике «Смета» нет колонок суммы (Цена × Кол-во по смете, Цена × Остаток) — управленчески полезно видеть бюджет и остаток в деньгах, не только в штуках.

### Сделано

- Схема справочника «Смета» (id 306906) расширена с 9 до **11 колонок**: добавлены «Сумма по смете» (Кол-во по смете × Цена, не меняется после импорта) и «Сумма остатка» (Остаток × Цена, пересчитывается вместе с остатком). У справочников Pyrus нет встроенных формул (в отличие от табличных полей формы, где «Сумма» считается сама) — эти два столбца просто числа, которые считает и пишет наш код (`smeta_catalog_import.py` при импорте, `smeta_remainder_bot.py` при пересчёте остатка).
- **Расширять схему УЖЕ существующего справочника пришлось через новый метод `PyrusClient.sync_catalog_schema()`** (`POST /catalogs/{id}` с полным списком колонок). Обычный `diff` (upsert/delete строк) колонки не меняет — это другой endpoint.
  - **Находка, не описанная в документации примером:** без `"apply": true` в теле запроса метод молча ничего не применяет — только возвращает предпросмотр (в ответе `"apply": false`). Первая попытка без этого флага прошла без ошибки, но при повторном чтении справочника ничего не изменилось — нашли по факту `"apply":false` в самом ответе.
  - Справочник пришлось предварительно полностью очистить (`diff` с `delete` по всем ключам) — не проверялось, что происходит со значениями существующих строк при одновременном добавлении колонки на непустом справочнике, применяли только на пустом ради безопасности.
- **Найден и исправлен баг точности:** формат `:g` (использовался для Цены/Кол-ва/Остатка с самого начала проекта) ограничивает ОБЩЕЕ число значащих цифр (6 по умолчанию), а не число цифр после запятой. У дорогих позиций (шестизначная и больше цена, например 836102.61 ₽) это тихо роняло точность до целых рублей ещё на этапе записи «Цены» — а любая сумма, посчитанная от такой урезанной цены, наследовала ошибку (доходило до ~1.5 руб. на позицию). Исправлено на `.2f` — сначала для самих сумм, потом (после того как расхождение всё равно осталось) и для «Цены» в источнике. Итоговая погрешность — не больше 0.01 ₽ (это уже просто шум округления float, не баг).
- **Ещё один найденный и исправленный логический баг в `smeta_remainder_bot.py`:** проверка «нужно ли обновлять строку» опиралась только на то, поменялся ли «Остаток» — если он уже случайно совпадал с посчитанным (например, из-за разницы во времени деплоя между сервером и локальной машиной), «Сумма остатка» могла остаться устаревшей навсегда, потому что код никогда не доходил до её пересчёта. Исправлено — теперь «Остаток» и «Сумма остатка» проверяются на актуальность независимо друг от друга.
- **Проверено end-to-end**: реальный повторный импорт (1234 строки) + тестовая заявка (заказ 5 при бюджете 1) + пересчёт остатка + отклонение заявки — суммы верны на каждом шаге, задеплоено на сервер, боевой крон подтверждённо работает с новой схемой.
